# Design System Forge · 设计系统锻造

把一套已验证的方法论和一份样板工程，锻造成属于用户自己的设计系统。
样板在 `assets/xuan-template/`（纸感编辑风 v0.1，五件套：tokens.css / SKILL.md / verify.mjs / index.html / README.md，已通过自身 verify 与逐屏截图自查）。

## 第 0 步 · 采集参数

已有信息从对话里取，缺什么用 AskUserQuestion 一次问齐（最多四问，每问给 2-4 个选项）：

1. **领地**——系统管哪类输出：AI 生成的文档与报告 / Web 产品与博客界面 / 幻灯片海报 / 还没想好
2. **执行者**——给谁执行：AI agent 为主 / 自己写代码为主 / 两者都要
3. **审美方向**——纸感编辑风 / 冷静极简 / 高对比现代 / 从我的作品反推
4. **名字**——用户提供；或按"一个有含义的词，名字即裁判"提议 2-3 个并各附一句含义

用户选"从我的作品反推"时，请他们给 3-5 个对味的产物（链接或截图），按 references/methodology.md 的反推法提炼，不要凭空替用户决定审美。

## 第 1 步 · 填推导链

按 references/methodology.md 的推导链逐层填写：领地 → 主张 → 铁律 → token → 决策表 → 验证。
各审美方向的参考值（主张样例、铁律样例、色板、字体倾向、verify 规则差异）查 references/presets.md。

硬性要求：

- 铁律 2~3 条，每条可判定、带理由；全部规则合计不超过 10 条
- 每条铁律至少对应一个 verify 检查
- 颜色的唯一事实来源是 tokens.css，其他文件禁止出现裸色值

## 第 2 步 · 生成项目

1. 复制样板：`cp -r <skill目录>/assets/xuan-template/ <名字>-design-system/`
2. 按顺序替换（样板里都有 TODO(你) 标记，搜 TODO 逐个处理）：
   - **名字**：目录名、`<title>`、hero、导航 brand、页脚题词（题词用一句话解释名字含义）
   - **主张**：hero lede 与 SKILL.md 的主张一节，用"我们 ____，不 ____"句式
   - **主色三件套**：定下 `--accent` 基色后，`--accent-ink` 取更深一档（hover 与小字号），`--accent-wash` 取极浅一档（标签底/选中底），`--ring` 同步换色
   - **审美差异值**：按 presets.md 调整灰阶、字阶、圆角、深度 token
   - **决策表与反面**：结合领地重写"要做什么怎么做"；反面至少 4 组，每组必须带原因
   - **verify.mjs**：规则必须匹配本次铁律——铁律变了规则就变（如极简风允许冷灰就删对应检查，深色底就加对比度检查）
   - **README**：推导链一节用本次真实的决策过程重写，不要照抄样板的措辞
3. 交付物中不要出现"思路受 XX 启发"之类的致敬或来源行。

## 第 3 步 · 质检（强制，跳过不得交付）

1. `node verify.mjs <项目目录>` 通过。
2. 反向测试：临时造一个含违规写法的文件，确认 verify 逐条拦截、退出码 1，然后删掉。只会说 pass 的检查器等于没有。
3. 浏览器截图自查介绍页（浏览器打不开 file: 链接，先用 node 起一个本地静态服务再逐屏截图）：
   - hero 的 serif 大标题是否真正加载了 webfont（显示成中易宋体说明加载失败，换 CDN 重试）
   - 每节布局、留白、组件观感；不满意就改 tokens.css 再看
4. 最后对照主张自查一遍：verify 只能证明没违反铁律，不能证明好看。

## 第 4 步 · 交付

给用户的说明固定包含四件事：文件清单及各自作用、留给用户的三处定制（名字/主色/主张）、verify 的用法、如何把生成物的 SKILL.md 挂成 agent 技能。
