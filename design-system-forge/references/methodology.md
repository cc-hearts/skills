# 方法论：推导链

一套设计系统的定义 = 回答一条推导链上的六个问题，顺序不能乱。
自洽感来自每一层都从上一层严格推导；做散了，几乎都是因为跳层——一上来就挑颜色、定组件。

## 六层

1. **领地——管什么，不管什么。** 一句话说清边界。领地决定技术选型（文档用 pt，界面用 rem），同时是一份"不做什么"清单，能拒绝 80% 的范围蔓延。
2. **主张——一句话当裁判。** 用"我们 ____，不 ____"句式。检验标准：没读过系统的人，凭这一句话就能判断某个设计"像不像你的"。
3. **铁律——2~3 条你愿意为之说 no 的规则。** 其余规则全部是它们的派生。每条要满足：能被机器判定；说得出为什么。说不出理由的规则，执行者第一个忽略。
4. **token——把铁律翻译成具体值。** 这一层只做翻译、不做新决策；冒出了铁律没覆盖的念头，回第三层升级成铁律，否则删掉。
5. **决策表和反面——执行者的操作手册。** "要做什么 → 怎么做"两列表覆盖 80% 高频场景；Don't/Do 成对且每组附原因；必须写兜底条款："表里没有的情况，回到第几条铁律自行推导"。
6. **验证——一条铁律至少一个检查。** 验证层是铁律的执行臂。一条铁律写不出对应检查，说明它还不够具体，回第三层重写。

## 可追溯性测试（定稿自检）

随机挑一条规则问"你从哪来"：token 要能爬到铁律，铁律要能爬到主张，主张要能爬到领地；爬不上去的一律删掉。
完整示例——"中文标题 500 封顶"（铁律，理由：中文缺少中间字重，浏览器合成加粗发糊）长出字阶 token，长出决策表"强调一个词用 serif 或主色、不加粗"，长出 verify 的字重检查。一条规则贯穿五层，系统才立得住。
这套测试通常能把初稿的四十条砍到十二条，砍完反而更好用。

## 反推法（用户说不清自己审美时）

1. 请用户收集 5 个觉得"对，就是这个感觉"的真实产物——别人的博客、一份 PDF、一张海报都行——并排摆在一起。
2. 回答五组二选一，强迫选边：**暖还是冷？衬线还是无衬线？一色还是多色？方还是圆？疏还是密？**
3. 把每个选择写成可判定的规则。"暖"不能停留在"暖"，要写成"中性色全部偏黄，禁默认冷灰"。
4. 从中挑出最不愿妥协的 2~3 条当铁律，其余降级成 token 或决策表条目。

选边无法代劳——这五组二选一是定义设计系统里真正属于用户的部分。

## 命名

一个有含义的词，名字要能反过来当裁判（纸、余白、宣纸都是这个路数）。给用户提议名字时，每个都附一句"这个名字如何约束设计"，比如取自纸，就意味着一切决策问"这在纸上好看吗"。

## 常见失败模式

- **从色板开始**，而不是从产物和场景开始 → 系统散，没有主张可依
- **规则超过 10 条** → 执行者必然漂移，规则越少执行越稳
- **规则不带理由** → 无法推广到没覆盖的场景，且第一个被忽略
- **没有验证** → 约定随时间漂移，改着改着就回到默认审美
- **没有兜底条款** → 表里没有的场景变成随机发挥
- **v1 就想做大而全** → 领地失控；从 v0.1 开始，先让三条铁律站得住
